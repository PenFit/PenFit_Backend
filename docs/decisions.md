# PenFit 백엔드 기술 결정 기록

2026 금융 AI Challenge 제출작. 결정 시점, 후보, 선택 이유를 남긴다.

## 서비스 한 줄 정의

사회초년생이 가상의 연금계좌로 생애 변화와 시장 하락을 미리 경험하고, AI 분석을 통해 유지 가능한 연금계획과 적합한 상품 후보를 찾는 서비스.

핵심 흐름: 사용자 정보 입력 → 가상 연금계좌 선택 → 6개 상황 리허설 → AI 행동 분석 → 연금 패스포트 → 연금계획 저장 → 상품 후보 추천

## 1. 런타임

### Spring Boot 3.5.16 (Java 17)

- **후보**: Spring Boot 4.1.1 / 3.5.x LTS
- **배경**: 초기 scaffold가 4.1.1로 생성돼 있었다.
- **결정**: 3.5.x LTS로 낮춤
- **이유**: 해커톤은 제출 기한이 고정이라 라이브러리 호환 문제로 시간을 잃는 것이 가장 큰 리스크다. Boot 4는 최신이라 springdoc·JWT·QueryDSL 등 주변 생태계 레퍼런스가 아직 얇다. 3.5.x는 동일하게 Java 17을 쓰면서 레퍼런스가 풍부해 막히는 구간이 거의 없다.
- **비용**: 최신 스택이라는 어필 포인트를 포기했다.

## 2. 데이터베이스

### PostgreSQL 16

- **후보**: PostgreSQL 16 / MySQL 8 / MariaDB 11
- **결정 기준**: AI 서버 응답을 어떻게 저장할 것인가 하나로 갈렸다.
- **이유**:
  1. AI 응답 원문을 `JSONB`로 통째 보관하면서 내부 필드로 조회까지 가능하다. 개발 중 AI 응답 스키마가 자주 바뀌는데, 원문을 잃지 않으면 근거를 항상 되짚을 수 있다.
  2. idle 메모리가 30~50MB로 MySQL(350~450MB)보다 훨씬 적다. 한 VM에 Spring·PostgreSQL·Caddy·Python AI 서버를 함께 올려야 해서 중요했다.
  3. 태그 배열을 네이티브로 다룰 수 있다.

### AI 응답 저장 방식 — 하이브리드

- **후보**: 전부 정규화 컬럼으로 펼치기 / JSON 통째 저장 / 혼합
- **결정**: 화면에 직접 쓰는 값만 컬럼으로 펼치고, 원문 전체는 `ai_raw_response(JSONB)`에 함께 보관
- **이유**: 컬럼만 쓰면 AI 응답 필드가 추가될 때마다 마이그레이션과 코드 수정이 필요하다. JSON만 쓰면 화면 조회가 번거롭다. 혼합하면 조회는 단순하고 스키마 변경에도 근거가 남는다. 참고 노트가 요구한 "증거 루프"와 "실패 로그"도 이 원문으로 충족한다.

### Flyway

- **후보**: JPA `ddl-auto: update` / Flyway
- **결정**: Flyway + `ddl-auto: validate`
- **이유**: 이 서비스는 시드 데이터가 많다. 시나리오 6개와 선택지 31개, 연금상품 12개, 가상 소비내역 34건, 심사용 데모 계정까지 코드로 관리해야 하는데 `ddl-auto`로는 데이터를 넣을 방법이 없다. 참고 노트가 요구하는 "같은 입력으로 회귀 테스트"도 DB 상태가 매번 동일하게 재현돼야 가능하다.

### Enum 검증을 3중으로

- **결정**: Java Enum + DB `CHECK` 제약 + 복합 외래키
- **이유**: 리허설 상황·선택지는 허용 조합이 31개로 정해져 있고, 선택지 코드가 상황 간에 재사용된다(예: `KEEP`은 이직·출산·시장하락에 모두 존재). 코드만으로 검증하면 버그 하나로 잘못된 조합이 저장된다. `rehearsal_answers`가 `rehearsal_scenario_options(scenario_code, option_code)`를 복합 FK로 참조하게 만들어, 애플리케이션에 버그가 있어도 DB가 막는다.
- **검증**: `MARRIAGE + REBALANCE` 삽입 시 FK 위반으로 차단되는 것을 확인했다.

## 3. AI 연동

### 별도 Python AI 서버 + 백엔드가 동기 REST 호출

- **후보**: 백엔드가 LLM API 직접 호출 / 별도 AI 서버 / AI 서버 콜백 / AI 서버가 DB 직접 접근
- **결정**: 팀에 AI 담당이 있어 FastAPI 서버를 분리하고, 백엔드는 `@Async` 스레드 안에서 동기 REST로 호출
- **이유**: 콜백 방식은 양쪽 상태 관리가 복잡해지고, AI 서버가 DB를 직접 만지면 스키마 결합도가 높아진다. 동기 호출은 AI 서버가 상태를 전혀 몰라도 되어 가장 단순하고 디버깅이 쉽다. 사용자에게는 `202 Accepted` 후 2초 폴링으로 비동기처럼 보인다.

### 숫자 계산은 백엔드, AI는 판정과 문장만

- **결정**: 복리·예상 연금자산·미션 효과 금액은 전부 Java 계산기가 산출한다. AI 서버는 성향 판정과 설명 문장만 반환한다.
- **이유**: 참고 노트의 원칙("숫자 계산을 생성형 AI에 맡기지 않는다")이자 금융 서비스의 기본이다. 생성형 AI가 만든 금액은 재현성과 검증 가능성이 없다.

### 타임아웃은 설정값으로 분리

- **결정**: `application.yml`의 `penfit.ai.timeout.*`로 빼고, AI 파트가 실측한 P95가 나오면 숫자만 교체한다.
- **이유**: 모델이 만들어지기 전에는 응답시간을 측정할 수 없다. 코드에 박아두면 실측 후 재배포가 필요하지만, 설정값이면 값만 바꾸면 된다. 이 덕분에 AI 서버 없이 백엔드를 먼저 완성할 수 있었다.

### Spring 타임아웃을 AI 타임아웃보다 3초 길게

- **이유**: AI 서버가 `504 MODEL_TIMEOUT`을 반환할 시간을 확보하기 위해서다. 같거나 짧으면 백엔드가 먼저 끊어버려서 실패 원인이 "타임아웃"인지 "네트워크 오류"인지 구분할 수 없다.

## 4. 인증

### 자체 JWT + Refresh Token은 DB 테이블

- **후보**: Redis / DB 테이블 / 저장하지 않음(stateless)
- **결정**: DB 테이블
- **이유**: stateless는 로그아웃과 강제 로그아웃을 구현할 수 없는데 명세에 로그아웃 API가 있다. Redis는 TTL 관리가 깔끔하지만 컨테이너와 운영 포인트가 하나 늘어난다. MVP 트래픽에서는 DB 조회로 충분하다.
- **구성**: Access Token은 응답 body, Refresh Token은 HttpOnly 쿠키.

### 게스트 모드 대신 심사용 데모 계정

- **배경**: 참고 노트 점검표에 "가능하면 로그인 없이 핵심 기능을 확인하는 게스트 체험을 제공"이 있다.
- **후보**: 게스트 모드 구현 / 데모 계정 발급 / 아무것도 안 함
- **결정**: 데이터가 모두 채워진 데모 계정을 시드로 제공
- **이유**: 게스트 모드는 인증과 데이터 모델 설계가 통째로 늘어난다. 데모 계정은 시드 데이터 작업만으로 같은 목적(심사위원이 막히지 않고 핵심 흐름을 본다)을 달성한다.

## 5. 도메인 데이터

### 리허설 시나리오 금액을 사용자 설정액으로 치환하지 않음

- **후보**: 사용자 납입액으로 치환 / 문서 원문 고정 / 상황문만 치환
- **결정**: 원문 고정
- **이유**: 리허설은 가정 상황이므로 사용자 상황에 맞출 필요가 없다. 디자인의 리허설 화면도 "현재 월 납입액 10만원"을 고정 카드로 보여주고 있어 일관된다. 치환 방식은 5만원 설정자가 "절반으로 줄인다"를 골랐을 때 하한(5만원)을 뚫는 문제도 있었다.

### 연금상품과 가상 소비내역을 DB 시드로

- **후보**: 공공 API 연동 / DB 시드
- **결정**: DB 시드
- **이유**: 공공 API는 연동 비용과 실패 지점이 늘어나는데 MVP 검증에는 기여하지 않는다. 대신 참고 노트 점검표를 지키기 위해 상품 테이블에 `data_source`와 `reference_date` 컬럼을 두고 화면에 노출한다.
- **주의**: 현재 시드의 수수료율·특징은 개발용 임시값이다. 제출 전 각 금융회사 공식 값으로 교체해야 한다.

### 가상 소비내역은 전체 사용자 공용 1세트

- **이유**: 심사위원이 여러 계정으로 확인해도 같은 결과가 나와 재현이 쉽다. 참고 노트가 요구하는 회귀 테스트에도 유리하다.

## 6. 인프라

### Oracle Cloud Always Free — A1을 포기하고 1GB AMD 인스턴스로

- **최초 계획**: Ampere A1 (4 OCPU / 24GB, ARM64). 비용 0원에 넉넉한 사양.
- **문제**: 인스턴스 생성 단계에서 Ampere 셰이프가 아예 목록에 뜨지 않았다. 서비스 한도를 조회하니 `standard-a1-core-count`의 서비스 제한이 **0**이었다. 재고 부족이 아니라 계정에 배정된 몫 자체가 0이라, 사양을 낮추거나 재시도해도 해결되지 않는다.
- **후보**: 유료 전환(PAYG) / 한도 증가 요청 / 다른 무료 호스팅 이전 / 남은 AMD Micro 사용
- **결정**: Always Free AMD `VM.Standard.E2.1.Micro` (1 OCPU / 1GB) 사용
- **이유**: 비용 0원을 유지하면서 지금까지 만든 배포 구성을 그대로 쓸 수 있다. 한도 증가 요청은 무료 계정에서 거절되는 경우가 많고 응답까지 며칠 걸려 해커톤 일정에 걸 수 없었다.
- **검증**: 추측 대신 실측했다. 컨테이너에 메모리 상한을 걸고 pgbench 동시 10 + HTTP 동시 200으로 부하를 태웠다.

  | 구성요소 | 실측 피크 | 상한 | OOM |
  |---|---|---|---|
  | Spring Boot | 259MB | 420MB | 없음 |
  | PostgreSQL | 143MB | 192MB | 없음 |
  | Caddy | 27MB | 48MB | 없음 |

  OS와 Docker 데몬을 더해 약 650MB / 1,024MB. 여유 약 370MB로 1GB에 들어간다.

- **파생 결정 1 — 아키텍처 전환, 그리고 되돌림**: AMD Micro는 x86_64라 기존 `arm64` 전용 이미지로는 컨테이너가 뜨지 않는다. 처음에는 amd64와 arm64를 각각 네이티브 러너에서 빌드해 매니페스트로 병합하는 멀티 아키텍처 구성을 택했다. 나중에 A1을 확보하면 그대로 배포할 수 있게 하려는 보험이었다.
  이후 이 보험을 걷어내고 `linux/amd64` 단일 빌드로 되돌렸다. A1은 재고 부족이 아니라 계정 할당량이 0이라 앞으로도 쓸 수 없어 보험의 대상 자체가 사라졌기 때문이다. 잡이 6개에서 3개로 줄어 파이프라인을 읽기 쉬워졌다. 실제 시간 절감은 30초 정도로 크지 않았고, 얻은 것은 단순함이다. ARM 서버를 쓰게 되면 되돌리는 데 30분이면 된다.
- **파생 결정 2 — 메모리 튜닝**: 1 OCPU 환경에서 G1GC는 오버헤드가 커서 SerialGC로 바꿨고, 힙을 256MB로 고정했다. Tomcat 최대 스레드는 200에서 50으로 줄였다. 기본값이면 스레드당 512KB 스택 때문에 최대 100MB를 차지한다.
- **파생 결정 3 — AI 서버 분리**: 남는 여유 370MB에 FastAPI(150~250MB)를 넣으면 안전 마진이 사라진다. AI 서버는 별도 호스팅하고 `AI_BASE_URL`만 연결한다. 백엔드는 주소만 알면 되므로 통신 규격은 바뀌지 않는다.
- **치른 비용**: 24GB에서 1GB로 줄었다. 트래픽이 늘면 감당하지 못하지만 MVP 심사에는 충분하다. 서버에서 여유 자원을 쓰는 작업(대용량 배치 등)은 설계에서 배제해야 한다.

### GHCR 이미지 방식 CI/CD

- **후보**: 서버에서 직접 빌드 / 레지스트리 이미지 pull / 수동 배포
- **결정**: GitHub Actions에서 이미지를 빌드해 GHCR에 올리고 서버는 pull만
- **이유**: 배포가 20~30초로 끝나고, 빌드가 실패해도 서버는 이전 버전 그대로 정상 동작한다. 심사 중 급하게 고칠 일이 생겼을 때 배포 속도와 롤백 용이성이 결정적이다. 서버에 JDK·소스·Gradle을 두지 않아도 된다.
- **부가 이점**: 저장소가 public이라 GitHub의 ARM64 러너(`ubuntu-24.04-arm`)를 무료로 쓸 수 있어 QEMU 크로스 빌드(5~10배 느림)를 피했다.

### Caddy (Nginx 아님)

- **후보**: 앱 포트 직접 노출 / 호스트 Nginx + certbot / Caddy 컨테이너
- **결정**: Caddy 컨테이너
- **이유**: 직접 노출은 HTTPS도, `/actuator` 차단도, 보안 헤더도 불가능하다. Nginx와 Caddy는 제대로 설정하면 보안 수준이 같지만, Caddy는 TLS 설정이 기본값으로 최신이라 실수할 여지가 적고 설정이 20줄로 끝난다. 결정적으로 Caddy는 컨테이너라 앱과 함께 배포·롤백된다. Nginx를 호스트에 두면 설정을 바꿀 때마다 서버에 SSH로 들어가야 한다.

### CI 브랜치 분리

- **결정**: `develop` 푸시와 PR은 테스트까지만, `main` 푸시에서만 이미지 빌드와 배포
- **이유**: 개발 중 커밋마다 이미지를 빌드하면 시간과 레지스트리 용량이 낭비된다. 배포는 최종 브랜치에서만 일어나야 한다.

## 7. 보안

금융 서비스이자 금융권 해커톤 제출작이라 기본값보다 한 단계 더 조였다.

### 서버 디스크에 비밀값을 파일로 남기지 않음

- **후보**: 서버에 `.env` 파일 유지 / GitHub Secrets에서 매 배포마다 `.env` 생성 / 파일 자체를 만들지 않음
- **결정**: 파일을 만들지 않고 배포 SSH 세션의 환경변수로만 전달
- **이유**: `docker compose`는 `${VAR}`를 셸 환경에서도 치환한다. 이 성질을 이용하면 서버 디스크에 평문 비밀번호가 남지 않는다. 서버가 탈취되어도 파일에서 읽어갈 값이 없다.
- **비용**: 서버에서 직접 `docker compose up`을 실행할 수 없다. 롤백은 Actions에서 이전 커밋 워크플로를 재실행하는 방식으로 한다.
- **안전장치**: 필수 값이 하나라도 비면 컨테이너를 올리지 않고 중단한다. 빈 문자열로 조용히 잘못 뜨는 상황을 막기 위해서다.

### actuator 외부 차단

- **배경**: actuator는 `/health` 외에도 `/env`(환경변수 전체), `/heapdump`(메모리 덤프), `/configprops` 등을 제공한다. Spring Boot 기본값은 `health`만 노출하지만, 디버깅하려고 `include: "*"` 한 줄을 넣는 순간 전부 열린다.
- **결정**: Caddy에서 `/actuator` 경로를 404로 차단하고, 노출 엔드포인트도 `health` 하나로 축소하며 상세 정보를 숨긴다.
- **영향 없음**: 컨테이너 내부 헬스체크는 `localhost:8080`을 호출하므로 그대로 동작한다.

### 포트 최소 개방

- **결정**: 22 / 80 / 443만 연다. 앱(8080)과 DB(5432)는 컨테이너 네트워크 안에만 둔다.
- **이유**: 8080을 열면 HTTPS를 우회할 수 있고 `/actuator` 차단이 무력화된다.

### 그 밖

- 컨테이너를 루트가 아닌 `penfit` 사용자로 실행
- GHCR pull 직후 `docker logout`으로 자격증명 파일 제거
- 보안 헤더(HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy) 적용, `Server` 헤더 제거
- 요청 본문 2MB 상한 (파일 업로드 기능이 없다)
- Swagger UI는 심사 편의를 위해 공개 유지 — 노출면을 감수한 의도적 선택

### yml 프로필 분리

- **결정**: `application.yml`은 `${}` 환경변수 뼈대만 담아 커밋하고, 실제 값이 들어가는 `application-dev.yml`·`application-prod.yml`은 `.gitignore`와 `.dockerignore` 양쪽에 등록해 커밋도 이미지 포함도 막는다.
- **이유**: 민감정보가 GitHub에 올라가는 사고를 구조적으로 차단한다. `.dockerignore`까지 등록한 것은 로컬에서 이미지를 빌드할 때 개발자 로컬 값이 이미지에 섞여 들어가는 것을 막기 위해서다.
- **검증**: 빌드한 이미지의 jar를 열어 `application-dev.yml`이 포함되지 않은 것을 확인했다.
- **예외**: 민감정보가 아닌 프로필별 동작(로그 레벨 등)은 `spring.config.activate.on-profile` 문서로 `application.yml` 안에 남겨 형상관리한다.

## 8. API 규약

### 공통 응답 전체 래핑

- **후보**: 성공·실패 모두 래핑 / 실패만 래핑
- **결정**: `{code, message, data}`로 전부 감싼다
- **이유**: 명세서에 이미 `FP4041`, `PN4092` 같은 커스텀 코드 체계가 있었고, 프론트가 응답 처리 유틸 하나로 통일할 수 있다.

### 에러코드 체계

- **결정**: `{도메인 2자리}{HTTP 상태 3자리}{일련번호 1자리}` (예: `FP4041` = 금융정보 + 404 + 1번)
- **이유**: 명세서에 이미 존재하던 두 코드의 규칙을 역산해 전체로 확장했다. 코드만 보고 어느 도메인의 몇 번 오류인지 바로 알 수 있다.
- **도메인 접두어**: CM 공통 / AU 인증 / US 사용자 / FP 금융정보 / PS 가상 연금 설정 / RH 리허설 / PP 패스포트 / PN 연금계획 / PR 상품 추천 / BM 행동 미션 / AI AI 연동

### 실제 HTTP 상태코드 사용

- 모든 응답을 200으로 내리지 않고 `202 Accepted`, `409 Conflict`, `422 Unprocessable Entity`를 그대로 쓴다.

## 9. 경계 상황 처리

참고 노트가 "정상·오류·경계 입력을 각각 준비하라"고 요구해서 미리 정했다.

| 상황 | 처리 |
|---|---|
| 여유자금이 0원 | 패스포트의 유지 가능액을 0으로 허용하되, 연금계획·상품추천 단계 진입 자체를 막고 "현재는 연금 납입보다 비상금과 현금흐름 확보가 먼저예요" 안내 |
| 조건에 맞는 상품 후보가 3개 미만 | AI 호출을 생략하고 `INSUFFICIENT_PRODUCT_CANDIDATES` 반환. 억지로 3개를 채우지 않는다 |
| 절감 가능액이 월 2만원 미만 | 미션을 만들지 않고 `NO_ACTIONABLE_SPENDING` 반환 |
| AI 분석 실패 | 리허설 상태를 `FAILED`로 두고 재시도 API 제공, `retry_count` 증가 |

## 10. 보류·후순위

- 수정(update) API 전반은 MVP 제외. 단 마이페이지의 닉네임 수정과 이메일 등록·수정·수신동의는 실제 이메일 발송의 전제조건이라 포함했다.
- IRP 중도인출 안내 문구를 어느 시나리오에 노출할지 미확정. 시나리오 응답의 `notice` 필드로 내려주도록 만들어서 DB 데이터만 바꾸면 되게 했다.
- 패스포트 "세부 분석" 탭 화면은 AI 응답의 `detailedAnalysis` 6건으로 채울 예정. API와 DB는 미리 준비해뒀다.
